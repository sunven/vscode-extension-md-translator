# d4. 结果回填、状态管理与可复用判断

## 本维度要回答的问题

- 翻译结果如何回填到页面或弹层 UI？
- 任务状态、loading、错误、取消或重试如何处理？
- 翻译结果是否缓存、持久化或与用户设置联动？
- 哪些模块适合复用，哪些地方需要改造？

## 搜索覆盖情况

本维度沿 d3 的响应处理继续做三轮源码定位：

- 第一轮追踪结果回填：从 `translation-modes.ts`、`translation-insertion.ts`、`translation-cleanup.ts`、`spinner.ts` 定位页面/节点翻译的 DOM wrapper、spinner、错误组件和恢复逻辑。
- 第二轮追踪状态与错误：从 `PageTranslationManager`、`translation-signal.ts`、`translation-state.ts`、selection toolbar provider 定位页面翻译状态、选区弹层状态、取消与重试。
- 第三轮追踪缓存与设置联动：核验 `translation-queues.ts`、Dexie 表、`db-cleanup.ts`、options 清缓存 UI、config change handler 和 background 注册入口。

停止理由：页面翻译、节点翻译、选区翻译三条主要结果展示路径均已定位；缓存、状态同步、错误重试和清理都有源码证据。未做浏览器动态运行测试，因此对复杂网页兼容性的判断仅限源码级分析。

## 关键发现

1. 页面/节点翻译的结果回填是直接改宿主 DOM，而不是在独立面板中展示。核心单位是带 `notranslate` 与 read-frog class/attribute 的 wrapper，避免译文再次被 walker 当作原文处理。

2. bilingual 与 translationOnly 是两套不同的 DOM 策略：
   - bilingual：保留原文，在目标节点后或内部插入 wrapper，再追加译文 span；inline/block 由 DOM 类型、强制块级规则和浮动布局检测决定。
   - translationOnly：先保存父节点原始 `innerHTML`，创建 `display: contents` wrapper，拿到译文后把译文 HTML 写入 wrapper，并移除原始 child nodes。

3. 停止翻译或切换状态时，清理逻辑会移除 wrapper 和错误 shadow host。translationOnly 模式额外从 `originalContentMap` 恢复原始内容；bilingual 模式通常只删除译文 wrapper。

4. 页面/节点翻译的 loading 是轻量 DOM spinner，不使用 React 批量挂载。翻译失败时才把错误 UI 作为 React shadow host 挂到 wrapper 中；错误 UI 包含重试按钮和 hover 详情，重试会按当前模式重新调用 `translateNodesBilingualMode` 或 `translateNodeTranslationOnlyMode`。

5. 选区翻译完全走 React 弹层状态机。LLM provider 分支使用 background stream，chunk 到达时更新 `translatedText` 和 `thinking`；关闭弹层、重跑或依赖变化会通过 AbortController 取消当前翻译。非 LLM provider 分支复用 `translateTextCore`，但展示仍在 selection popover 内完成。

6. 页面翻译状态存在 background 的 tab/session storage 中，并可携带 origin scope。popup、浮动按钮、content script 通过消息同步 enabled 状态；主 frame 导航离开启用翻译的 origin 时会清掉状态，同源 SPA 变更则倾向 restart。

7. 缓存分两类：翻译结果缓存和网页/字幕摘要缓存。翻译缓存 key 由文本、provider、语言、prompt、AI content-aware 和上下文等构造；background 命中时直接返回。缓存 7 天自动清理，也可在 options 页面手动清空翻译相关缓存。

8. 配置与 UI 联动是增量的：页面翻译开启前会校验 provider/language/translate config；翻译模式变化时若页面翻译处于 active 状态，会 stop 并 start，避免旧 wrapper 与新模式混合。

## 分析

read-frog 的展示层是“页面沉浸式翻译 + 选区弹层翻译”的双轨设计。

页面翻译追求在原网页结构中就地显示，因此实现重心是 DOM walk、wrapper 隔离、notranslate 标记、ShadowRoot/iframe 兼容、批量 DOM 操作、清理恢复和布局判断。这种方式用户体验接近浏览器翻译插件，但对宿主页面侵入更深：translationOnly 依赖保存和恢复 `innerHTML`，遇到复杂前端框架、水合状态、事件绑定或动态节点时存在破坏页面内部状态的风险。

选区翻译追求即时交互和流式反馈，因此更接近普通 React 应用状态管理。它不需要直接改原文 DOM，失败、取消、重新生成和 provider 切换都更容易控制；代价是不能自然承担整页沉浸式翻译。

状态管理分层较清楚：background 维护 tab 级 enabled 和缓存，host content manager 维护 observer/walk/title 运行状态，React/Jotai 维护 UI 展示状态。这个分层让多入口能共享一个页面翻译开关，也让 iframe 注入、同源导航和 popup/floating 状态同步成为可能。

缓存与队列是可复用价值较高的部分。`RequestQueue`、`BatchQueue`、Dexie cache、prompt token 和 provider dispatch 与 DOM 的耦合较低；但当前消息名、WXT storage、browser runtime port 和 config shape 与扩展架构强绑定，迁移到普通 Web/Node 服务时需要抽象通信与持久化接口。

## 对终稿的贡献

本维度可为终稿提供三类材料：

| 主题 | 可进入终稿的判断 | 关键文件 |
|---|---|---|
| 结果展示 | 页面/节点翻译直接插入 DOM；选区翻译用 React 弹层流式展示 | `translation-modes.ts`, `translation-content.tsx` |
| 状态与错误 | background 维护 tab 状态，manager 维护运行状态，页面错误可就地重试，选区错误在弹层 alert 中展示 | `translation-signal.ts`, `page-translation.ts`, `TranslationError` |
| 缓存与复用 | Dexie 缓存、队列、provider/prompt 层较适合复用；DOM 回填和 WXT message/storage 需要改造 | `translation-queues.ts`, `app-db.ts`, `message.ts` |

可复用建议：

- 适合直接学习或迁移的模块：provider 分流思路、prompt token 化、RequestQueue/BatchQueue、Dexie 翻译缓存、流式 port 协议、错误重试 UI 思路。
- 需要适配后再复用的模块：DOM traversal/filter、wrapper 插入、translationOnly 恢复、ShadowRoot/iframe 注入、WXT message/storage、浏览器权限与 content script 生命周期。
- 不建议直接搬运的部分：与 read-frog 配置 schema、i18n、analytics、toast、具体 UI 组件库耦合较深的上层组件。

## 不确定性与空白

- 未在真实浏览器中运行复杂网页样本，因此 DOM 侵入、translationOnly 恢复、ShadowRoot 和 iframe 的边界兼容性只做源码级判断。
- 缓存 key 包含 providerConfig 与上下文，理论上能降低误命中，但没有实测不同配置迁移或配置字段顺序变化对缓存命中的影响。
- 选区 LLM 流式路径未明显复用 `translationCache`；源码不能确认这是性能/隐私/交互上的刻意取舍，还是尚未优化。
- GitHub issue/讨论受 API rate limit 与 `sn-search-code` 依赖缺失影响，未形成完整外部使用反馈证据。
