# d3. 模型 Provider、Prompt 与请求执行

## 本维度要回答的问题

- read-frog 支持哪些翻译 provider 或模型配置方式？
- 翻译 prompt、system message 或结构化输出如何组织？
- 请求执行是否使用流式输出、重试、错误处理或缓存？
- API key、base URL 等敏感配置如何流转？

## 关键发现

1. provider 分为三类执行路径：
   - 非 API 翻译 provider：`google-translate`、`microsoft-translate`，直接调用公开/边缘翻译接口。
   - 纯翻译 API provider：`deeplx`、`deepl`，使用对应 API 或 background fetch 代理。
   - LLM provider：OpenAI、DeepSeek、Gemini、Anthropic、OpenRouter、Ollama、Tensdaq、SiliconFlow、Volcengine、MiniMax、Alibaba、Moonshot、HuggingFace 等，通过 AI SDK 统一成 language model。

2. 页面翻译、节点翻译和非流式选区翻译最终都可以落到 `translateTextCore -> enqueueTranslateRequest -> translation-queues -> executeTranslate`。这个路径有缓存、限速、重试和 LLM 批处理。

3. 选区 LLM 翻译刻意走另一条流式路径：`SelectionTranslationProvider.translateWithLlm -> streamBackgroundText -> runtime port -> background streamText`。它不等完整翻译结束才显示，而是在 chunk 到达时更新 `translatedText` 和 thinking 状态。

4. prompt 是可配置模板，不是硬编码单句。默认 system prompt 要求专业目标语言母语翻译、只输出译文、保持段落和 HTML 标签、保留专名/代码；prompt tokens 支持 `{{targetLanguage}}`、`{{input}}`、`{{webTitle}}`、`{{webContent}}`、`{{webSummary}}`。batch 模式会追加 `%%` 分隔规则。

5. LLM 页面翻译支持批处理，非 LLM 页面翻译不走 batch queue。`shouldUseBatchQueue(providerConfig)` 对 LLM 返回 true，BatchQueue 按 provider/language 分组，并限制最大字符数和条目数；批量输出数量不匹配时重试，必要时回退为单条请求。

6. 缓存发生在 background 的 Dexie `translationCache`。content script 在 `translateTextCore` 中构造 hash，包含准备后的文本、providerConfig、语言、LLM prompt、AI content-aware 开关、网页上下文片段以及额外标签；background 命中缓存时直接返回规范化结果。

7. API key 与 baseURL 来自用户配置存储，不来自构建环境注入。`getModelById` 从 `local:config` 读取 providerConfig，再把 `apiKey`、`baseURL`、headers 交给 AI SDK provider factory；WXT production 构建阶段会阻止除 PostHog 外的 `WXT_*_API_KEY` 被打包。

## 分析

read-frog 的翻译请求层有两个目标：降低成本和改善交互。

页面翻译的特点是请求数量多、文本碎片多，所以它使用 background 队列、Dexie 缓存、hash 去重、token bucket 限速、LLM batch 合并和失败重试。这个路径牺牲了逐字流式展示，但换来了批量场景下的吞吐和成本控制。

选区翻译的特点是一次只处理一段用户关注文本，交互即时性更重要。因此 LLM provider 使用 runtime port 流式输出，支持 AbortController 取消和 reasoning/thinking 展示。非 LLM provider 没有流式能力，仍复用 `translateTextCore`。

provider 抽象做得比较宽：普通翻译 API、DeepL/DeepLX 和大量 AI SDK provider 都能作为“翻译 provider”。但它并不是完全统一的抽象：Google/Microsoft/DeepL 需要语言码转换与专用 HTTP 解析，LLM 需要 prompt、model、providerOptions 和上下文，DeepL/DeepLX 有背景 fetch / baseURL / apiKey 特殊逻辑。

## 对终稿的贡献

终稿可使用如下“请求执行链路”：

| 场景 | 调用链 | 响应形态 | 缓存/批处理 |
|---|---|---|---|
| 页面/节点翻译 | `translateTextForPage -> translateTextCore -> enqueueTranslateRequest -> executeTranslate` | 非流式，完成后插入 DOM | Dexie 缓存；LLM 可批处理 |
| 选区翻译 LLM | `translateWithLlm -> streamBackgroundText -> background streamText` | 流式 chunk + thinking | 未走页面翻译 BatchQueue |
| 选区翻译非 LLM | `translateWithStandardProvider -> translateTextCore` | 非流式 | 走 background 队列与缓存 |
| Translation Hub | `TranslationCard -> executeTranslate` | 非流式 mutation | 直接执行，未显式走 translationCache |
| 自定义选区 AI action | `streamBackgroundStructuredObject -> background streamText Output.object` | 流式结构化对象 | 依赖结构化 schema，非翻译主线 |

## 不确定性与空白

- provider/model 列表可能随代码更新频繁变化；本报告以 `main@c9b157ad` 为准。
- Google Translate 与 Microsoft Translator 的非官方/边缘接口稳定性不由项目控制，源码只体现调用方式和错误处理。
- 未实测各 provider 的真实 API 行为；结论限于源码级实现机制。
- Selection LLM 流式路径没有使用页面翻译的 Dexie translationCache，这可能是设计选择，也可能是后续可优化点；源码未看到显式缓存。
