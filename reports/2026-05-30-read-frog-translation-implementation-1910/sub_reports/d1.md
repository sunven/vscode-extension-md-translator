## 关键发现

1. read-frog 是 WXT 驱动的 MV3 浏览器扩展，不是单一网页应用。翻译功能分布在 popup、floating button、context menu、host content script、selection content script、background service worker 与共享工具层之间。

2. 页面翻译有多个触发入口，但最终都收敛到 background 的翻译状态消息，再由 host content script 内的 `PageTranslationManager` 执行：
   - popup 按钮发送 `tryToSetEnablePageTranslationByTabId`；
   - 页面浮动按钮发送 `tryToSetEnablePageTranslationOnContentScript`；
   - context menu 的页面菜单调用 `askManagerToTogglePageTranslation`；
   - host runtime 还注册页面翻译快捷键和四指触控手势。

3. 节点翻译是 host content script 内部的就地点选翻译：`registerNodeTranslationTriggers` 根据配置监听 hotkey 或 click-and-hold，命中后调用 `removeOrShowNodeTranslation(point, config)`。

4. 选区翻译是独立的 selection content UI：选中文本后 `SelectionToolbar` 读取 `window.getSelection()`，生成选区快照和上下文快照；点击 toolbar 或右键菜单后打开翻译弹层。

5. 后台 background 是跨上下文协调层：`translation-signal.ts` 维护页面翻译状态与 iframe 注入同步，`context-menu.ts` 处理右键入口，`translation-queues.ts` 处理页面翻译请求队列，`background-stream.ts` 处理选区 LLM 流式输出。

## 分析

入口设计呈现“多入口、单状态、分任务执行”的结构：

- 页面翻译入口不直接翻译 DOM，而是先修改或查询 tab 级翻译状态，再让 host content script 的 manager 开始/停止。这样 popup、浮动按钮、右键菜单、快捷键和自动翻译都能共享状态。
- host content script 是页面翻译和节点翻译的执行现场，因为它能访问 DOM、selection、shadow root、iframe 等浏览器页面环境。
- background 不是 DOM 翻译执行者，而是承担状态同步、跨 frame 注入、请求队列、缓存、provider 调用和 stream port 的服务角色。
- selection content script 是专门 UI 层，原因是选区工具栏需要 shadow DOM、React state、弹层定位和流式展示；它复用底层 provider/translate 工具，但触发链与页面整页翻译不同。
